# Tether product and engineering audit

Date: 4 October 2026. Status: audit complete; proposed roadmap, not an implementation-completion report.

Tether has a valuable differentiator: a Slack conversation can continue the actual coding session, with its tools, working tree and history. The project needs to turn that continuation engine into a comprehensible, programmable team of colleagues that finishes work. The largest opportunities are product coherence, durable task ownership, shared context, useful collaboration and contributor accessibility.

The previous roadmap overemphasized one delivery-recovery incident and fleet operations. That work belongs inside execution correctness. It is superseded as the overall product roadmap by [ROADMAP.md](../ROADMAP.md).

## What was audited

Three independent reviews plus a root source/executable review covered:

- [Architecture](2026-10-04-architecture.md): ownership, host coupling, drivers, state, outbound paths, tasks and memory.
- [Behavior](2026-10-04-behavior.md): admission, collaboration, speech/silence, context, progress, controls and evaluation.
- [Open-source experience](2026-10-04-open-source.md): installation, CLI, packaging, release identity, documentation and contribution.

The inspected sources were deliberately distinguished:

| Source | Revision or identity | Meaning |
| --- | --- | --- |
| Current public repository main | `b7b9d0ff8542b289a8389a8d01d9f5ba65705af0`, authenticated GitHub API and fetch, 3 October 22:23 UTC | What a contributor can obtain from main. |
| Latest colleague/recovery development line | `60ef226d9d7c36514c9aa24ffcdd940d5ba8f9c1` | Carries newer local execution, delivery and context work; not equivalent to public main. |
| Installed local runtime source | Selected read-only Hermes/Tether paths and file hashes in the architecture review | Integration evidence; not a claim about all machines or a stock Hermes release. |

Main and the development line differ across 28 Tether files, with 6,385 additions and 953 deletions including tests and docs. README, package metadata, architecture and compatibility documents are byte-identical between those two revisions despite substantial implementation differences. Source comparison is retained in the audit workspace's `.cascade/source-scope.json`.

No live Slack message, model inference, production gateway restart or installation occurred during this audit. Test processes used temporary HOME directories, explicit environment allowlists, disabled live Herdr discovery and fake transports. Heavy tests ran under the machine's bounded batch runner. The earlier 45-workspace test leak was not reproduced.

## Executive findings

| Finding | Evidence | Engineering implication |
| --- | --- | --- |
| **The public front door is broken.** | Package/plugin0.4; README beta0.3; a documented `--herdr` setup flag is rejected; advertised cockpit and schema assets are absent; anonymous official npm query returned E404 at audit time. OSS review records exact scope. | Make installation, help, documentation, defaults and one actual distributable describe the same product. |
| **The best demonstrated behavior lives on another code line.** | Public native driver has its own Claude process pump; newer code uses Hermes's transport, correlation and prepared delivery. Public/main and local/install semantics differ. | Consolidate into a contributor-visible source of truth; selectively port and reconcile capabilities, preserving supported behavior. |
| **Tasks are mostly instructions layered over turns.** | Tether stores endpoint/binding/turn/attempt/delivery facts; collaboration prompt tells agents to use tasks. External preparation receives `task_id=attempt_id`. | Connect a stable goal/task to its session, attempts, dependencies and artifacts through the existing Hermes task service. |
| **Collaboration heuristics can lose useful work.** | Offline probe: substantive `:warning:` review is treated as status; thanks is admitted. Same-peer cap is about actor sequence, not progress. | Typed transport notices, task/review events and contextual attention decisions; meaningful resource budgets. |
| **Fresh context is a model responsibility.** | Current admitted message bundle and native history do not guarantee latest decisions, current artifact revision or unresolved objections. Optional preparation fails open. | A provenance-bearing context builder and task/project memory tools across runtimes. |
| **Status conflates several different truths.** | `auth.test` becomes transport-connected; polling health is hardcoded true; ready turns are called queued deliveries; native completion is not task completion. | Project task, execution and delivery state separately into clear user-visible status. |
| **The evaluation rewards appearances.** | Promise and delivered-artifact examples have identical structural scores. Export excludes roots with zero replies. Judge sees shortened messages without artifact evidence. | Measure accepted task outcomes, corrections, follow-through and cost, using replayable task episodes. |
| **Runtime and product policy are tangled.** | Candidate runtime6,160 Python lines; active1,824, driver1,321; driver owns transport plus persistence/finalization. | Extract responsibilities around a real consumer; typed adapters and host services, not a framework rewrite. |
| **Platform authority has two paths.** | Native finals can use Hermes ledger; roots, explicit replies and files still go through raw-token SlackEgress. | A common Hermes platform facade, keeping transient reactions distinct from durable messages. |
| **The default team belongs to Parcha.** | Shipped system-prompt roster contains real local people, Slack IDs, roles and hosts. | Neutral colleague manifest and reusable collaboration contract; organization configuration remains instance data. |

These are observed source/probe findings. The audit cannot infer acquisition or retention from them: no adoption analytics or new-user interviews were available. The product wedge and prioritization are engineering recommendations to validate through actual use.

## Executable checks and their limits

### Public main

The actual installed Hermes Python interpreter ran the public source's 11 Python unittest files in separate processes against a private temporary HOME: **267 tests, all 11 files passing**. Receipt: `.cascade/public-main-baseline/receipt.json` in the audit workspace.

This is a meaningful baseline for those Python tests. It does not prove a clean stock-Hermes install, npm publication, the advertised cockpit, live Slack ingress, intelligent collaboration, or the full CI matrix. The test suite does not exercise several front-door and behavioral counterexamples found above.

### Development line

The initial isolated per-file run executed478 tests. It exposed stale mute/failure-notice APIs, launcher test assumptions, prompt-contract differences and newer native-spawn expectations. Eight initial CLI failures were caused by the audit runner setting XDG_STATE_HOME while those fixtures changed HOME without replacing the inherited state path. A corrected focused run passed all32 CLI tests. The initial receipt is retained; it is not presented as44 product defects.

A full corrected run with private HOME and default private XDG paths completed at01:04 UTC: **478 tests across14 files;9 files pass and5 fail**, with36 failure/error reports across those files. Receipt: `.cascade/candidate-corrected-baseline/receipt.json`. The failing files are notices, plugin registration, active behavior, Store and broker; native-driver171 and saved-answer46 tests pass. Failure cohorts need reconciliation before combining the locally evolved implementation with public main. Do not drop expectations solely to obtain a green number: decide the supported contract and test that contract.

### Product and behavior probes

Safe CLI/help/package checks observed missing commands/flags/assets and release inconsistencies. Those mechanical probes used Node20, outside the declared Node22/24 support boundary; parser/source evidence corroborates the reported defects. Package dry-run enumerated46 files and665,275 unpacked bytes; it did not test installation. The anonymous official registry E404 is a point-in-time observation, not publication history.

Pure behavior probes reproduced identical promise/artifact metrics and warning-review suppression on public main as well as the development line. They establish policy/evaluation counterexamples, not actual current Slack incidents. Historical native/receipt canaries and Jev results retain their original narrow scope in the behavior audit. In particular, an older Jev shadow mislabeled5/8 work-needed messages; typed answers were not evidence of good decisions.

## Product and architecture decision

Build **an AI team workspace in Slack, backed by real native computers**. A developer can begin with one existing session, then add a reviewer or other colleague. The team owns useful work, preserves context, shares artifacts, incorporates corrections and continues after waiting. Slack and an optional cockpit show the same actual work state.

Make one explicit division of responsibility:

1. **Hermes:** platform interface and credentials, observed task/dependency services, memory/tool access, reusable native execution services and platform delivery, through advertised supported host capabilities.
2. **Tether:** colleague configuration; external-session attachment; conversation/task/execution relationships; collaboration and context orchestration; a human-facing projection of work.
3. **Computer adapters:** exact-session attach/start, owned input, typed activity and results, cancellation and explicit capabilities. Claude Code and Codex first; Herdr placement optional; Grep integration after its actual API is mapped.
4. **Jev:** optional narrow semantic judgments about attention, context relevance and useful collaboration. Deterministic ownership/control stays in code; uncertain judgments can invoke richer reasoning or fetch context rather than simply silence work.

Prefer an existing native Hermes path for newly created Slack work when the selected host advertises that capability, and Tether's attachment path for externally created sessions. Present one product; do not launch two writers for one session. Reuse supported existing tasks and memory rather than creating a competing database and scheduler.

The visible vertical slice leads the implementation: task → implementer → artifact → reviewer finding → correction → completed result → same-session follow-up. Architectural extractions happen as this workflow needs them. A giant driver rewrite, new authority daemon, fleet rollout or all-backend parity is not a prerequisite for making that slice useful.

## What this audit delivered

- Three independent evidence-backed reviews and a source comparison across current main, development and local installed integration.
- Fresh isolated Python baselines, safe product probes and preserved failures.
- [A broad roadmap](../ROADMAP.md) covering experience, architecture, task autonomy, context, semantic judgment, runtime extension and OSS growth, with an explicit first build tranche.

The implementation of that roadmap is future work. This audit does not claim the proposed product already exists, that source/test inconsistencies are fixed, or that any new runtime feature is deployed.

1. The one-paragraph verdict

Recall is a write-dominated system built like a read-heavy one. In the last 24 hours the MCP served about 50 tool calls while the collectors wrote about 1,100 objects. Each ingested record ends up as text in seven places and vectors in four, six of them inside a managed Postgres whose buffer cache cannot hold its own derived indexes. Every change to a live session re-projects the whole session, so the database rewrites ~150k passages a day for ~320 documents, keeps its cache cold, and falls two days behind on freshness. Meanwhile the read path that already scales and that the literature now favors, the agent running code over raw evidence in S3, is the one Recall pioneered and under-invests in. The fix is not a bigger database. It is to make Postgres a catalog, move the search plane next to the evidence on object storage, project incrementally at turn granularity, and add a reranker and session recaps on top. Done in that order, each step is measurable with the systems card and none needs a rewrite.

2.2 Data model: seven copies of every record

Full text lives in the S3 raw object, canonical_events.canonical_redacted, canonical_documents.text_redacted, canonical_chunks.text_redacted plus its generated tsvector, the evidence JSONL parts, canonical_passages.text_redacted plus its tsvector, and the Parquet passages dataset. Vectors live in chunk, passage, representation, and legacy tables. Only the S3 parts and the passages are on the paths that matter. The legacy plane is still written for Slack webhooks and read by the /v1 routes.

2.3 Flows: full replacement on every change

  • Per record: one S3 PUT, one canonical transaction that inserts the event, flips the previous document to not-current, inserts the document and N chunks, writes an audit row, and upserts tenant, principal, source and grant rows (four identity writes per request, one of them an unconditional UPDATE).
  • Per session change: the logical-evidence projector rebuilds every JSONL part; the passage projector deletes all passages of the document and re-copies them, re-attaching embeddings by content hash; the Parquet projector rebuilds all four datasets for the whole source-month. A growing Codex session with 500 passages does this every collector cycle it changes.
  • Per MCP call: one authorization audit row on its own connection before any read.
  • Reads: search uses passages GIN and HNSW plus a chunk-liveness join; show, session_context, and related read the 79 GB chunk table directly; exec and scan read S3 through Archil and touch Postgres only for the catalog.

4. Target architecture

4.1 Principles

  • One authority, derived indexes. S3 raw objects and evidence parts are the truth. Everything else is a projection that can be rebuilt from them, cheaply, incrementally.
  • Postgres is a catalog. It answers "which documents, whose, when, where are they" in milliseconds and stays small enough to live in cache on a modest tier. It stops holding text, tsvectors, and vectors.
  • The unit is the turn. A user message with its assistant reply and tool calls, with a stable id. Growing sessions append turns; nothing already indexed is rewritten. Embedding cost scales with new content only.
  • Search lives next to the evidence. Lance datasets on S3 give vector plus BM25 plus SQL in one format that DuckDB already reads, so search and scan query the same files and code mode gets the index for free. turbopuffer is the managed fallback with the same outbox.
  • The agent is the retriever. Search returns compact candidates with receipts; open and exec do the reading; recaps and decisions give it a short path for the common questions. Budget for the tokens; that spend is what makes it good.
  • Everything gated by the card. No change ships without a before and after on latency, recall, freshness, and cost.

Postgres today is 108 GB because it holds six derived copies; as a catalog it is an order of magnitude smaller. The current design cannot reach 500 seats on any Postgres tier: 1.8B canonical_chunks rows with a global GIN is not a thing.

6. What not to do

  • Do not buy PS-320 to hide the churn. It works until the next 10×.
  • Do not build a knowledge graph over everything. Our questions are single-entity with a time filter; recaps and dated facts cover them at 1% of the cost.
  • Do not replace verbatim text with extracted summaries anywhere in the index. Supplement only.
  • Do not bring back a server-side retrieval agent. The caller is the agent; give it better tools and receipts.
  • Do not switch embedding models during H1-H3. Re-embedding the corpus is the exact storm that cost $800; do it once, after the turn projection exists, with the card as the ruler.

7. What makes it dope

Nobody else has a company's entire agent history, Slack, and docs as one corpus with receipts, people, and time, queryable by the agents themselves in code. The 2026 evidence says that is the winning shape. The work above is not a pivot; it is removing the six copies, the rewrite-everything projector, and the database-as-index habit that keep it from behaving like what it already is.

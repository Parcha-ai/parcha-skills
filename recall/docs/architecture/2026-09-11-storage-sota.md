# Storage & Index Architecture Briefing — transcript brain, 400k passages / 12M chunks → 10–100×

Date: 2026-09-11. Confidence markers: **[firm]** = vendor doc or changelog; **[soft]** = third-party blog/benchmark; **[est.]** = my arithmetic.

## 1. Postgres-native options (2025–26)

- **pgvector versions.** 0.8.0 (2024-10-30) added iterative index scans (`hnsw.iterative_scan = relaxed_order|strict_order`, capped by `hnsw.max_scan_tuples`, default 20k), better cost estimation for filtered queries, faster HNSW scans/inserts/on-disk builds. 0.8.1 (2025-09) = PG18 + faster `binary_quantize`. 0.8.2 (2026-02-26) is a security fix (CVE-2026-3172, buffer overflow in parallel HNSW build) — upgrade. `halfvec`/`bit` indexing arrived in 0.7.0. **[firm]** https://api.pgxn.org/src/vector/vector-0.8.1/CHANGELOG.md · https://www.postgresql.org/about/news/pgvector-082-released-3245 · https://docs.pgedge.com/pgvector/v0-8-1/filtering/
- **Filtering reality.** HNSW/IVFFlat know nothing about `WHERE`; the index returns global top-k, PG filters after. Iterative scan fixes "too few rows" but at CPU cost proportional to selectivity. Recommended ladder: (a) partial HNSW index per known predicate (tenant, `is_active`), (b) native partitioning by tenant/workspace so the planner prunes, (c) materialized-CTE pre-filter + brute-force exact scan when the filtered subset is a few thousand rows. **[soft, consistent across sources]** https://mydba.dev/blog/pgvector-filtered-search · https://clickhouse.com/resources/engineering/scale-vector-search-postgres · https://github.com/pgvector/pgvector/issues/980
- A March 2026 arXiv study of filtered vector search *inside Postgres* finds page-access / filter-check overheads dominate, and graph-based inline filtering (ACORN/NaviX-style) often loses to clustering-based indexes in a real DB — i.e., optimal strategy is selectivity- and I/O-dependent, not fixed. **[firm paper, general finding]** https://arxiv.org/abs/2603.23710
- **Quantization.** `halfvec` halves storage/index size with negligible recall loss (Neon, Katz). Binary quantization (`bit`, `binary_quantize()` expression index) → ~32× smaller index, requires a rerank step over the full vector; good fit for a two-stage pipeline. **[soft]** https://neon.com/blog/dont-use-vector-use-halvec-instead-and-save-50-of-your-storage-cost · https://jkatz05.com/post/postgres/pgvector-scalar-binary-quantization/
- **Churn / maintenance.** pgvector HNSW never compacts deleted graph nodes; searches keep walking dead nodes. Guidance: `REINDEX INDEX CONCURRENTLY` after >~10% deletes, prefer UPDATE over DELETE+INSERT, tighten autovacuum scale factor on the embeddings table. Index build must fit `maintenance_work_mem` or falls to a 10–50× slower disk build. **[soft]** https://perun.au/insights/pgvector-production/ · https://mydba.dev/blog/pgvector-scaling-large-datasets · https://medium.com/engineering-layers/signal-driven-health-monitoring-for-hnsw-indices-w-pgvector-ba35d9a6e575
- **pgvectorscale (StreamingDiskANN + SBQ).** Disk-oriented, filter-aware ("streaming" post-filter), ~471 QPS @99% recall on Timescale's April 2026 numbers, viable to ~50M vectors. **Shipped on PlanetScale Postgres.** Weak spot: insert throughput (VectorChord's benchmark shows ~107 inserts/s vs 1,565 for VectorChord — vendor benchmark, treat as directional). **[firm availability / soft perf]** https://planetscale.com/changelog/postgres-extension-vectorscale · https://github.com/timescale/pgvectorscale · https://docs.vectorchord.ai/vectorchord/benchmark/pgvectorscale.html
- **VectorChord (IVF + RaBitQ).** Best-in-class Postgres QPS at high recall and very fast builds; **not available on PlanetScale** (only "requested"). **[firm]** https://ps-extensions.io/ · https://blog.vectorchord.ai/vector-search-over-postgresql-a-comparative-analysis-of-memory-and-disk-solutions
- **BM25 on Postgres.** tsvector+GIN: GIN stores no lexeme positions, so `ts_rank` forces a heap (and TOAST) read for every candidate — ranking is I/O-bound at scale, no index-only ranking, and `ts_rank` isn't BM25. RUM stores positions and can return ordered results from the index, at the cost of slower builds/inserts and generic-WAL bloat. ParadeDB `pg_search` (Tantivy-backed covering BM25 index) fixes ranking properly but: **not on PlanetScale**, and Neon is *removing* it (new projects blocked since 2026-03-19, removal 2026-09-21); ParadeDB pushes BYOC or a logical-replication sidecar off RDS/CloudSQL. `pg_textsearch` (Tiger) and `vchord_bm25` exist, also not on PlanetScale. **[firm]** https://postgrespro.com/docs/enterprise/16/rum · https://supabase.com/docs/guides/database/extensions/rum · https://www.paradedb.com/blog/introducing-search · https://neon.com/docs/extensions/pg_search · https://docs.paradedb.com/deploy/byoc · https://www.tigerdata.com/blog/introducing-pg_textsearch-true-bm25-ranking-hybrid-retrieval-postgres

**Implication:** on PlanetScale specifically, the ceiling is pgvector 0.8 + pgvectorscale + tsvector/GIN. Real BM25 means leaving Postgres for the lexical leg.

## 2. Object-storage-native search

- **turbopuffer.** S3 is authority; per-namespace WAL + index prefix; NVMe/RAM cache. SPFresh centroid ANN + inverted BM25 + exact metadata filters, strongly consistent. Cold first query on a 1M-doc namespace ≈ 500–870 ms p50; warm ≈ 8–14 ms; writes batch to 1 WAL entry/s/namespace, ~165–200 ms commit. Storage ~$0.02/GB; April 2026 added "namespace pinning" (pay GB-hours for hot capacity when >~10 QPS). Namespaces are the natural tenant partition. **[firm docs / soft pricing]** https://turbopuffer.com/docs/architecture · https://turbopuffer.com/docs/tradeoffs · https://www.morphllm.com/comparisons/turbopuffer-vs-pinecone · https://turbopuffer.com/blog/turbopuffer
- **LanceDB / Lance format.** Versioned columnar format on S3 (every write = queryable snapshot), vector + BM25 FTS + SQL on same dataset, DuckDB can read Lance natively (DuckDB blog May 2026). Appends write new fragments atomically; unindexed rows are brute-forced at query time until `optimize()` folds them in; compaction is background but not free. OSS: you run the compaction/indexing cadence; Enterprise automates it. Fits your existing Parquet+DuckDB+Archil sandbox unusually well. **[firm]** https://docs.lancedb.com/indexing/reindexing · https://duckdb.org/2026/05/21/test-driving-lance · https://lance.org/format/index/ · https://www.lancedb.com/blog/newsletter-january-2026
- **Quickwit/Tantivy.** Stateless searchers over immutable splits on S3, sub-second, ~10× cheaper than Elastic for logs; lexical only, append-oriented; no ANN. Good template for "index is derived, cheap at rest". **[soft]** https://github.com/quickwit-oss/quickwit · https://blog.elest.io/quickwit-s3-sub-second-log-search-without-elasticsearch/
- **Amazon S3 Vectors** (GA Dec 2025): cheapest at rest, 2B vectors/index, but high/unpredictable latency and costs ramp hard with query volume; AWS's own guidance is tier to OpenSearch for hot. **OpenSearch Serverless NextGen** (GA May 2026) scales to zero, removing the old ~$700/mo floor. **[firm/soft]** https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors.html · https://hidekazu-konishi.com/entry/amazon_s3_vectors_design_decision_guide.html · https://darryl-ruggles.cloud/the-real-cost-of-vector-storage-s3-vectors-vs-opensearch-vs-pgvector-vs-pinecone/
- **Milvus 3.0 (July 2026)** Storage V3 + Woodpecker WAL are fully S3-backed with hot/warm/cold tiering; **Weaviate** offloads whole tenants to S3 (v1.26+); **Qdrant** has no true S3 tier. All three are heavier ops than the above. **Vespa** is superb for real-time ranking but is an always-on cluster — wrong cost shape for a bursty brain. **[firm docs]** https://milvus.io/docs/woodpecker_architecture.md · https://docs.weaviate.io/weaviate/starter-guides/managing-resources · https://sacra.com/research/ai-engineer-indeed-turbopuffer-vespa-elasticsearch/
- **Elasticsearch searchable snapshots** give S3-at-rest, but Enterprise tier only. **[soft]** https://agentset.ai/vector-databases/compare/turbopuffer-vs-elasticsearch

Best fit for "S3 authority, derived index, cheap at rest, fast enough hot": turbopuffer (managed) or Lance (self-run, aligns with your DuckDB stack).

## 3. Streaming / incremental indexing for append-only sessions

- **Append-only passage projection beats whole-document re-projection** for growing transcripts: cost scales with delta, not corpus. Key by `(doc_id, chunk_ordinal)` and store a content hash per chunk; skip embedding when hash matches; delete-by-doc mapping lets you tombstone stale chunks. Idempotent writes make replay safe. **[soft, industry consensus]** https://www.useparagon.com/blog/rag-freshness-incremental-sync-deduplication · https://nstarxinc.com/blog/from-data-lake-to-rag-factory-the-technical-view-building-incremental-embedding-pipelines-without-melting-your-cloud-bill/
- **Engine behaviour on updates:** Elasticsearch/Lucene segments are immutable — any update = delete + full re-index of the doc, and per-segment HNSW graphs must be merged (CPU-heavy). Lance: append = new fragment, visible immediately, indexed lazily via `optimize()`; deletes are tombstones until compaction. pgvector: in-place graph insert per row; deletes leave dead nodes (see §1). **[firm]** https://medium.com/rocksetcloud/updates-inserts-deletes-challenges-to-avoid-when-indexing-mutable-data-in-elasticsearch-c0eeff595865 · https://docs.lancedb.com/indexing/reindexing
- **Cadence.** No vendor gives a universal number. Constraints that set it: turbopuffer coalesces to 1 WAL write/s/namespace (so sub-second debounce is wasted); Lance/Elastic degrade with fragment/segment count, so batch appends and compact on a timer. **Reasonable default [est.]:** debounce hot sessions 30–120 s (only re-chunk the tail window that crosses a chunk boundary), flush batches, run index `optimize`/compaction every 5–15 min or every N fragments, and a nightly full compaction. CDC/outbox: write the projection intent to an outbox row/table in the same transaction as the session append, drain it with a worker — standard pattern; nothing search-specific.

## 4. Cost / latency facts

- **Memory sizing [est.]:** halfvec 512-d = 1,024 B/vector; pgvector HNSW (m=16) adds ~200–400 B of neighbour lists → ~1.3–1.5 KB/vector. If the 12M chunk rows carry embeddings: ~16–18 GB index today; 10× → ~170 GB; 100× → 1.7 TB, which no sane managed-PG RAM tier holds. If only 400k passages are embedded, even 100× (40M) is ~55 GB — feasible on a 64–128 GB Metal box. Third-party rule-of-thumb "20–25 KB/vector" is for 1536-d float4 — don't apply it here. https://mydba.dev/blog/pgvector-scaling-large-datasets
- **PlanetScale Metal:** local NVMe included in price, tiers from 1 GiB RAM/$50 up; NVMe softens the "index must fit RAM" rule versus network storage, but HNSW random reads still want buffer-cache residency. **[firm]** https://planetscale.com/blog/50-dollar-planetscale-metal-is-ga-for-postgres · https://planetscale.com/docs/postgres/pricing
- **S3-native:** turbopuffer quotes S3+SSD cache ≈ $70/TB/mo vs ~$1,600/TB/mo RAM-resident; cold p50 ~0.5–0.9 s per namespace, warm ~10 ms. Namespace-per-tenant multiplies cold starts — pin or pre-warm the few hot ones. **[firm/soft]** https://turbopuffer.com/docs/architecture · https://jxnl.co/writing/2025/09/11/turbopuffer-object-storage-first-vector-database-architecture/
- **Egress pitfalls:** keep the index engine in the same region as the S3 authority; cross-region or cross-cloud (PlanetScale ↔ S3 ↔ Archil sandbox) egress at ~$0.02–0.09/GB will dwarf storage cost when you re-project 79 GB of text. S3 Vectors bills per query bytes scanned — bursty-but-large indexes get expensive. **[soft]** https://darryl-ruggles.cloud/the-real-cost-of-vector-storage-s3-vectors-vs-opensearch-vs-pgvector-vs-pinecone/
- **Cache warming on Postgres:** `pg_prewarm` (shipped on PlanetScale) with `autoprewarm` in `shared_preload_libraries` records buffer contents and reloads after restart/failover; `pg_prewarm('idx','buffer')` for the HNSW index on a fresh replica. Replicas each need their own warm cache. **[firm]** https://www.postgresql.org/docs/current/pgprewarm.html · https://ps-extensions.io/

## 5. Multi-tenant isolation vs ANN performance

- **Row-level filter on one global HNSW:** traversal visits other tenants' nodes and discards them; with 1,000 tenants and 0.1% share, most hops are wasted → iterative scan or huge `ef_search`. **[soft]** https://kulekci.medium.com/multi-tenant-vector-search-in-practice-building-a-shared-knowledge-base-with-qdrant-7b7928ba00fe
- **Partition/partial-index per tenant (Postgres):** planner prunes to the tenant's own graph; best filter performance but N indexes to build/maintain and pgvector has no "tiered" mode. Partial indexes stop being manageable past a few dozen tenants; declarative partitioning (`pg_partman` is on PlanetScale) scales further. https://mydba.dev/blog/pgvector-filtered-search
- **Dedicated engines:** Qdrant `payload_m=16, m=0` builds a per-tenant sub-graph inside one collection; v1.16 adds tiered multitenancy (small tenants shared, large tenants own shards) and explicitly discourages collection-per-tenant. turbopuffer = namespace per tenant (native, cheap at rest, cold-start per namespace). Weaviate offloads idle tenants to S3. **[firm]** https://qdrant.tech/documentation/manage-data/multitenancy/ · https://turbopuffer.com/docs/tradeoffs · https://docs.weaviate.io/weaviate/starter-guides/managing-resources
- For a shared brain with one tenant today and a shared corpus, the cheap answer is a tenant column + partitioning by *workspace/project*, not per-user; only isolate when ACL or size demands it.

## What I'd do (400k → 40M passages)

Keep PlanetScale as the transactional authority for sessions, passages metadata and ACLs; stop treating it as the search index for anything past ~5–10M vectors. Immediately: upgrade to pgvector 0.8.2, embed **passages** (not 12M chunks) as `halfvec(512)`, partition/partial-index by workspace, turn on `hnsw.iterative_scan=relaxed_order`, `pg_prewarm` the index, and `REINDEX CONCURRENTLY` on a churn threshold. That covers the next 10× on a mid-size Metal tier.

For the 100× path, project passages from S3 into **Lance** (option C) — it's the only candidate that is S3-native, gives vector + BM25 + SQL in one file format, and slots into the DuckDB/Archil sandbox you already run. Outbox in Postgres → worker appends fragments with content-hash reuse, `optimize()` every ~10 min, nightly compaction. If owning compaction proves annoying, swap the derived index to turbopuffer (option B) with the same outbox — the projection code is identical.

Uncertainties: Lance's FTS maturity vs Tantivy/turbopuffer at 40M docs is under-benchmarked publicly; PlanetScale may ship pg_search/VectorChord (both "requested"), which would extend option A; my per-vector index sizes are arithmetic, not measured.

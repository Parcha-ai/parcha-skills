# Agent Memory Systems, 2025–2026: briefing for a transcript-first company brain over MCP

## 1. Designs, benchmarks, and what actually wins

- **Letta/MemGPT.** Tiered memory (in-context "memory blocks" + recall + archival, pgvector-backed), plus "sleep-time compute" that offloads memory rewriting to an async agent ([Letta](https://www.letta.com/blog/sleep-time-compute/)). Letta's own Aug 2025 benchmark: a plain agent with **filesystem tools (grep/open/search)** scored 74.0% on LoCoMo with GPT-4o-mini, above Mem0's 68.5%; their conclusion is that tool-use competence beats retrieval-mechanism cleverness, and that memory should be evaluated on end-task performance ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory/)).
- **Mem0.** Write-time fact extraction with add/update/delete consolidation. Paper claims 26% relative LLM-judge improvement over OpenAI memory on LoCoMo, 91% lower p95 latency and >90% token savings vs full-context; the graph variant adds only ~2% ([arXiv 2504.19413](https://arxiv.org/abs/2504.19413)). Their 2026 self-reported numbers (92.5% LoCoMo, 94.4% LongMemEval) use different judges/models than competitors and are not comparable ([mem0](https://mem0.ai/blog/ai-memory-benchmarks-in-2026)).
- **Zep/Graphiti.** Bi-temporal knowledge graph: `valid_at/invalid_at` (world time) plus `created_at/expired_at` (transaction time) on every edge; new facts invalidate old edges instead of deleting them ([arXiv 2501.13956](https://arxiv.org/html/2501.13956v1), [Zep blog](https://blog.getzep.com/beyond-static-knowledge-graphs/)). Zep's rebuttal to Mem0: LoCoMo conversations are only 16–26k tokens (a full-context baseline gets ~73%, beating Mem0's 68%), it lacks knowledge-update questions, has ground-truth defects, and Mem0 misconfigured Zep (single-user model, timestamps appended to text, serial searches); corrected Zep scores 75.1% ([Zep](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)).
- **Cognee / LangMem / A-MEM / MemoryBank.** LangMem formalizes semantic (facts/profile), episodic (past successful cases), and procedural (evolving instructions) memory ([Atlan survey](https://atlan.com/know/types-of-ai-agent-memory/)). A-MEM builds Zettelkasten-style linked notes that get rewritten as new memories arrive ([arXiv 2502.12110](https://arxiv.org/pdf/2502.12110)). Cognee is vector+graph hybrid. None of these has strong independent benchmark evidence; treat as design references.
- **Anthropic.** Memory tool (`memory_20250818`) is a client-side file directory (view/create/str_replace/insert/delete/rename); you own storage, path scoping, and PII stripping. Paired with server-side context editing and compaction: Anthropic reports +39% on a 100-turn task and 84% token savings ([docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool), [blog](https://claude.com/blog/context-management)). Claude Code auto-memory writes per-project MEMORY.md + topic files and per-session `summary.md`, extracting every ~5k tokens ([docs](https://code.claude.com/docs/en/memory), [claudefa.st](https://claudefa.st/blog/guide/mechanics/session-memory)).
- **OpenAI / Google.** ChatGPT: explicit "saved memories" + implicit "reference chat history," and since June 2026 "Dreaming," a background pass that rewrites the user model across years of chats ([OpenAI](https://help.openai.com/en/articles/8590148-memory-faq), [mem0 writeup](https://x.com/mem0ai/article/2071990201531118063)). Google: Gemini "personal context" and Vertex AI Memory Bank, which is LLM extraction of facts/preferences from transcripts into a per-user store ([Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/vertex-ai-memory-bank-in-public-preview)). Both are write-time extraction, consumer-shaped.
- **Graph RAG family.** GraphRAG-Bench: vanilla RAG matches or beats graph RAG on simple fact retrieval (83.2% evidence recall); graphs win on multi-hop/summarization (HippoRAG 87.9–90.9% vs 64.5%); MS-GraphRAG global queries cost up to ~330k tokens, HippoRAG2 ~1k vs ~950 for vanilla ([arXiv 2506.05690](https://arxiv.org/html/2506.05690)). LazyGraphRAG defers all summarization to query time: index cost equal to vector RAG, 0.1% of full GraphRAG, and wins on Microsoft's own BenchmarkQED ([MSR](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)); vendor-run, treat with caution.
- **Benchmarks.** LoCoMo (1,540 Qs, short), LongMemEval (500 Qs, ~115k tokens, knowledge updates + abstention), BEAM (up to 1M tokens), MemBench ([mem0 survey](https://mem0.ai/blog/state-of-ai-agent-memory-2026)). **LongMemEval-V2** (May 2026) is the most relevant to you: 451 questions over up to 500 agent trajectories (115M tokens) covering state recall, state tracking, workflow knowledge, "environment gotchas"; a **coding agent over trajectory files in a sandbox (72.5%) beat the best RAG (48.5%)** ([arXiv 2605.12493](https://arxiv.org/pdf/2605.12493)). Critiques: benchmarks leak entity tokens so lift is misattributed ([Entity-Collision, 2605.29630](https://arxiv.org/pdf/2605.29630)); reliability degrades unevenly as irrelevant sessions pile up (HippoRAG lost 16–20 points) ([2605.07313](https://arxiv.org/pdf/2605.07313)).

**Net:** in 2026 the evidence favors "raw logs + strong search + code execution" over heavy write-time graphs for long agent histories; graphs earn their cost only on multi-hop and temporal-update questions.

## 2. Memory types and what pays off for engineering-history questions

- **Working memory** = context window management (compaction, context editing). Solved by the model vendor; do not rebuild.
- **Episodic** = the transcripts/Slack threads themselves. Read-time retrieval over raw logs is the winner in LongMemEval-V2 and Letta's filesystem result; it also preserves provenance for receipts.
- **Semantic** = extracted facts/entities/decisions. Write-time extraction is cheap per event and lets you answer "what did we decide about X" without re-reading 40 sessions, but it drifts: Hindsight's example is an agent asserting Postgres six weeks after a MySQL migration because a stale fact outscored the new one. Their levers: importance filter at write time, entity merge, recency decay, eviction only for compliance ([Hindsight](https://hindsight.vectorize.io/blog/2026/05/21/agent-memory-consolidation)).
- **Temporal validity.** Bi-temporal facts (Graphiti model) are exactly what "what did we decide about X, and has it changed" needs; the cost is an LLM pass per event to detect contradictions. A cheaper middle ground: store decisions as dated, source-linked facts and let retrieval sort by `valid_at` descending, invalidating only when a later extraction explicitly supersedes.
- **Recap/session-summary indexes.** Claude Code's `summary.md` per session and Letta's sleep-time consolidation are both this pattern. For "who worked on Y last week" and "how did we fix Z," a per-session recap (what, why, files touched, outcome, actors, timestamps) indexed alongside raw records is the highest-leverage addition: cheap to produce, gives a small candidate set, and every claim can be traced back to the raw transcript.
- Mapping: **"what did we decide about X"** → decision facts with time + citation, fallback to recap search. **"who worked on Y last week"** → structured metadata (actor, repo, timestamp) queried by code, not embeddings. **"how did we fix Z"** → recap search then open raw session. Uncertain: no public benchmark measures these engineering-history question types; LongMemEval-V2's "workflow knowledge" and "gotchas" categories are the closest.

## 3. Retrieval tool contracts for agents

- **Search → open → exec.** Anthropic's Nov 4, 2025 "code execution with MCP": expose tools as files on disk for progressive disclosure, filter large results in the sandbox, persist intermediate state as reusable skills, tokenize PII at the client; 150k → 2k tokens on a sample task ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)). Follow-ups: Tool Search Tool (BM25/regex variants, ~85% token reduction on MCP evals) and Programmatic Tool Calling (Python in a managed container calls tools; only the script output enters context; ~38% fewer billed input tokens on a 75-tool benchmark) under the `advanced-tool-use-2025-11-20` header ([docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)). Cloudflare Code Mode converts MCP tools into a TypeScript API and has the model write code: 32% savings on simple tasks, 81% on batch, 2,500 endpoints in ~1k tokens ([Cloudflare](https://blog.cloudflare.com/code-mode/), [InfoQ Apr 2026](https://www.infoq.com/news/2026/04/cloudflare-code-mode-mcp-server/)).
- **MCP spec 2026-07-28.** Stateless core (protocol version, client identity in `_meta`; `Mcp-Method`/`Mcp-Name` headers for gateway routing); server-initiated requests replaced by Multi Round-Trip Requests (`resultType: "input_required"` → client retries with `inputResponses`), which is how elicitation now works on stateless servers; Tasks moved to the `io.modelcontextprotocol/tasks` extension with poll-based `tasks/get` and `tasks/update` for long-running work; `structuredContent` can be any JSON value; list results carry `ttlMs`/`cacheScope` for catalog caching; Roots, Sampling, Logging, and HTTP+SSE deprecated ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/), [Stacktree](https://stacktr.ee/blog/mcp-2026-spec-changes)). Partial results are not first-class in the spec; the practical pattern remains cursor pagination plus a Task for anything over a deadline.
- **Budgets and receipts.** Nothing standardized; the emerging practice is per-call `deadline_ms`/`max_results`, returning a compact hit list with stable record IDs, and a separate `show`/`exec` step that yields citable receipts. Your existing recall server already has this shape.

## 4. People, identity, authorization, deletion

- **Cross-source attribution.** No memory product does Slack↔git↔agent-session identity resolution out of the box; the pattern in enterprise agent guides is a canonical person row with per-provider identity rows resolved server-side, never by the model ([freeCodeCamp handbook](https://www.freecodecamp.org/news/ai-agent-per-user-oauth-slack-github/)). Uncertain: I found no published accuracy numbers for email/handle/committer matching.
- **Scoping.** Mem0 scopes reads/writes by `user_id/agent_id/app_id/run_id`, and recommends tenant-scoped filters at the storage layer plus audit logs per retrieval ([mem0 governance](https://mem0.ai/blog/ai-agent-memory-governance-meaning-best-practices-for-secure-memory)). Anthropic's memory tool leaves all of this to your handler, including path-traversal defense.
- **Deletion.** Mem0 offers `delete_all` by identity/metadata and 1000-item batch deletes ([docs](https://docs.mem0.ai/core-concepts/memory-operations/delete)). The hard part is cascade: deletion in the canonical store must propagate to every derived projection (embeddings, extracted facts, recaps) or the index keeps surfacing removed content ([Oracle](https://blogs.oracle.com/developers/from-rag-to-memory-systems-building-stateful-ai-architecture)). Graphiti's `expired_at` and Hindsight's "make stale unretrievable without deleting" are for correctness, not compliance; GDPR-style erasure still needs hard tombstones that projectors honor.

## 5. Evaluation practice and SLOs

- Offline truth sets + LLM judge (question, gold, generated answer) is universal; judge reliability and error cascades through tool chains are themselves under study ([AgentProp-Bench](https://arxiv.org/pdf/2604.16706)). Component-level evals (retriever, tool, planner separately) are recommended over end-to-end only ([Confident AI](https://www.confident-ai.com/blog/llm-agent-evaluation-complete-guide)).
- Fix the retriever confound: BM25 as a mandatory baseline and stratify by query type ([Entity-Collision](https://arxiv.org/pdf/2605.29630)); test at realistic store sizes because degradation is nonlinear ([2605.07313](https://arxiv.org/pdf/2605.07313)).
- Latency numbers (vendor-published, treat as indicative): chat agents ~200ms retrieval budget, enterprise copilots ~400ms inside a 3s window; size buffers to P95 not P50; Supermemory claims sub-400ms at scale; Mem0 claims 91% lower p95 than full-context ([Supermemory](https://supermemory.ai/blog/latency-budgets-memory-retrieval), [Mem0 paper](https://arxiv.org/abs/2504.19413)). No neutral published SLO for agent tool calls exists that I could find.

## Design implications for a transcript-first company brain over MCP

**Add**
1. **Per-session recaps** (what/why/outcome/files/actors/time), produced at ingest and re-indexed on session close. Highest leverage per dollar; the LongMemEval-V2 and Claude Code evidence both point here.
2. **Decision and entity extraction as dated, source-linked facts** with `valid_at/superseded_by`, not a full temporal graph. Answers "what did we decide about X" with a receipt and a date; supersession handled by a later extraction explicitly pointing back.
3. **Structured actor/time metadata queryable by code** (DuckDB over parquet is already the right shape). "Who worked on Y last week" is a filter, not a semantic search.
4. **Canonical person table with per-source identity rows**, resolved server-side; every record carries `actor_id` and `source_grant`.
5. **Hard tombstones honored by every projector** (records, passages, recaps, facts, embeddings), with a re-projection job.
6. **Eval harness**: a truth set of engineering-history questions, BM25 baseline, LLM judge, run at production store size, P95 latency per tool.

**Skip**
- Full GraphRAG / Graphiti-style graph over everything: only pays on multi-hop and costs 100x+ at index time; your questions are mostly single-entity with a time filter.
- Rebuilding working memory; leave compaction to the harness.
- Consumer-style user-profile "memory"; wrong shape for shared engineering history.

**Uncertain**: whether extracted decision facts beat recap search alone for your question mix; run both against the truth set before committing to the extraction pass.
